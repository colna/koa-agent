# 代码导读 —— 如何读懂这个项目

> 目标读者：想通过一个**真实可运行**的小项目学习「HTTP 服务 + LLM Agent + 运维工具集成」工程实践的开发者。
> 用法建议：**先跑起来 → 按「阅读路线」逐站读源码 → 对照每个文件旁的测试 → 最后做「动手练习」**。
> 源码中的所有教学注释与本导读互相引用，读到不明白处可直接搜注释里的关键词。
> **路径约定**：以 `src/...` 开头的路径均指 server 包（完整为 `apps/server/src/...`）；web 前端见「第 6 站」；skill 脚本见「第 7 站」。

## 0. 先跑起来（建立直觉）

```bash
pnpm install
pnpm dev:server                      # 没有 key 也能启动，只是对话接口会报 502
pnpm dev:web                         # 浏览器打开 http://127.0.0.1:3001
pnpm test                            # 全仓 145 个测试（server 126 + web 19）全离线，不需要任何 key
```

用 curl 发一轮对话（有真实 key 时），观察 `POST /agent/chat` 返回什么、SSE 接口的逐段输出长什么样 —— 先知道「它做什么」，再读「它怎么做」。完整冒烟步骤见 [技术文档 §10](02-技术文档.md)。

可选增强（不配也能跑测试）：SP 工具的 `SP_ADMIN_TOKEN`、SLS 的 `~/.sls_creds` 或 OAuth profile、BytePlus 的 `BYTEPLUS_ENV_FILE` —— 全部**缺失不阻塞启动**，工具运行时才给配置指引。

## 1. 一分钟系统全景

```
浏览器（apps/web，Next.js，:3001）
  └─ fetch 直连 server（跨域由 CORS 放行；对话走 SSE 流式读取）
       └─ Koa 服务（apps/server，:3000）：
            HTTP 请求
              └─ Koa 中间件链（app.ts 装配）
                   logger（记日志）→ error（统一错误信封）→ cors → bodyparser → router
                     └─ routes/：校验入参（zod）→ 调用 Agent / 会话存储
                          ├─ agent/graph.ts：LangGraph 状态图
                          │    ├─ model 节点（调 LLM；输入前经 trimHistory 裁剪上下文）
                          │    ├─ tools 节点（执行工具）← 二者循环直到模型不再要工具
                          │    └─ checkpointer（SQLite/内存）：按 thread_id 记住多轮会话
                          ├─ agent/threads.ts：会话列表 / 删除（直接读 checkpointer 的 SQLite）
                          └─ 工具集（注入图）：
                               ├─ sp-tools.ts     SP 运维 6 工具（信号/错误/报表/在线/看板）
                               ├─ skills.ts       sls_query_log（spawn sls_query.py）
                               └─ byteplus.ts     byteplus_query（spawn byteplus-query.mjs）
```

对话链路：`/agent/chat`（一次拿完整回复）与 `/agent/chat/stream`（SSE 逐 token + 工具过程帧）。两者共用同一张图和同一套会话存储；web 默认走流式。会话管理：`GET/DELETE /agent/threads`、`POST .../rewind`（撤回）。

## 3. 核心概念速览（初学必读）

- **Koa 与中间件洋葱模型**：`app.use(mw)` 按顺序包成洋葱，每个中间件 `await next()` 进内层、回来再执行剩下的代码。错误从内层向外冒泡，所以「logger 在外层」能既记成功也记失败。
- **zod**：运行时校验库。schema 既是校验规则也是类型来源（`z.infer`）。本项目用它做三件事：env 校验（fail-fast）、请求体校验（422 + details）、**工具入参 schema**（LangChain tool 用它生成 Function Calling 定义）。
- **LangGraph StateGraph**：把 Agent 逻辑写成「状态机图」——**状态**是一份数据（这里主要是 messages 数组），**节点**是函数（读状态、返回局部更新），**边**决定下一步去哪；条件边按函数返回值路由。图式写法的好处：循环（工具调用）与中断恢复被框架统一处理。
- **ReAct 工具调用循环**：模型被 `bindTools` 告知工具 schema → 需要时返回 `tool_calls` → `ToolNode` 执行工具、把结果作为 ToolMessage 追加 → 再问模型 → 直到模型不再要工具，输出最终文本。`src/agent/graph.ts` 就是这个循环的最小实现。
- **checkpointer / thread_id**：每一步图状态按 `thread_id` 存快照。新一轮 `invoke` 只用传新消息，历史自动从快照恢复 —— 这就是「多轮会话」的实现方式。**改写状态**同样可行（`updateState` + `RemoveMessage`）——「撤回」就是这么实现的。
- **Skill 接入模式（本项目的扩展点）**：skill = SKILL.md（name/description 进 system prompt 的能力索引，渐进式披露）+ 可执行脚本。要接入一个 skill，写一个「spawn 脚本 + 凭证注入 + 永不抛异常」的工具包一层即可（`skills.ts` / `byteplus.ts` 是两个样例）。
- **SSE（Server-Sent Events）**：一条长连接上的文本协议，帧格式 `event: xxx\ndata: json\n\n`；适合服务器单向推送（LLM 逐 token 输出）。本项目在标准帧外扩展了 `tool.start` / `tool.end` 过程帧。
- **stream-events 协议（本项目的关键选择）**：LangGraph 的经典 `streamMode:"messages"` 在 1.x 对本项目这类自定义模型只回**聚合后的最终消息**；逐 token 必须让自定义 callback handler 声明 `lc_prefer_chat_model_stream_events = true` 并实现 `handleChatModelStreamEvent`，从 `content-block-delta`（`text-delta`）里取增量。代码在 `src/agent/streaming.ts`，实测记录见 [技术文档 §5](02-技术文档.md)。
- **content-blocks（内容块）**：core 1.x 里消息的 `content` 可能是字符串，也可能是块数组（`[{type:'reasoning'…},{type:'text',…}]`）。流式路径下 AI 消息常是后者；取文本一律用 `message.text`（自动跳过 reasoning），不要假设是字符串（§6-4）。
- **上下文裁剪**：模型上下文有限，长会话不能无限送历史。`trimHistory` 按粗略 token 预算从末尾累计，对齐 human 消息边界（不拆散 tool_calls 与 ToolMessage 的配对），只影响「模型看什么」，checkpointer 里始终全量。
- **依赖注入与可测试性**：全项目没有「模块级单例」——config、model、graph、router、log 都从参数传入（`createApp({log, routes})`、`createAgentGraph({model, checkpointer})`）。测试因此可以注入 FakeChatModel 与静音日志，而不碰真实环境。

## 4. 一次请求的完整旅程（走读）

以 `POST /agent/chat {"message":"查一下最近30分钟 error 日志"}` 为例：

1. **Koa 中间件链**（`src/app.ts`）：logger 记开始时间 → error 挂好兜底 → bodyparser 把 JSON 解析成 `ctx.request.body`。
2. **路由**（`src/routes/agent.ts`）：`chatRequestSchema.parse(body)` —— 校验失败在这里抛 `ZodError`（最终变 422）；通过后取/生成 `threadId`。
3. **invokeAgent**：调 `graph.invoke({messages:[{role:'user',content:...}]}, {configurable:{thread_id}})`。
4. **图内循环**（`src/agent/graph.ts`）：checkpointer 按 thread 恢复历史 → `trimHistory` 裁剪 → model 节点调 LLM（模型要求调 `sls_query_log`）→ 条件边路由到 tools 节点（spawn 脚本、结果以 ToolMessage 追加）→ 回 model 节点 → 模型给出最终文本 → 条件边 `END`。
5. **回到路由**：`lastAiReply()` 取最后一条有文本的 AI 消息 → `ctx.body = {threadId, reply}`。
6. **出门**：logger 记录状态码与耗时；客户端拿到 JSON。

**SSE 版（`/agent/chat/stream`）差异在第 3~5 步**：路由先把响应头切成 `text/event-stream`（`ctx.respond=false` 接管原始 `res`），再给图挂上 `TokenStreamHandler`（自定义 callback）→ 模型每吐一个 token，core 回调 `handleChatModelStreamEvent` → 路由立刻写出 `event: message.delta`；同时从 updates 流里识别 model 节点（带 tool_calls → `tool.start`）与 tools 节点更新（→ `tool.end`），让前端能渲染工具过程卡 → 图跑完后补 `event: message.done` → `res.end()`。

**撤回的旅程**（`POST /agent/threads/:id/rewind`）：路由 `getState` 读出消息流 → 从末尾往回找最后一条 human 消息 → 把它及其之后的全部消息包成 `RemoveMessage`（按消息 id）→ `graph.updateState` 写回 → 下一轮对话的上下文里这段问答已不存在。前端配套把问题文本填回输入框（`preset`），实现「撤回并重新编辑」。

## 6. 必读「坑」（代码注释与文档里都有对应）

1. **Koa 隐式 404 上赋 `ctx.body` 会变 200**：未匹配路由时 status 是「默认 404」（非显式），直接赋 body 会触发 setter 把状态重置为 200。所以 `src/middleware/error.ts` 兜底时先 `ctx.status = status` 再赋值。详见 `30-Resources/troubleshooting/koa-server-gotchas.md`（个人知识库）。
2. **classic `streamMode:"messages"` 只回聚合消息**：细节与替代方案见 §3「stream-events 协议」；实现前做过探针实测，结论沉淀在知识库 `langgraph-js-streaming.md`。
3. **pnpm 10 默认拦截原生构建**：`better-sqlite3` 的安装脚本被忽略会导致运行时报错；解法是在 `package.json` 声明 `pnpm.onlyBuiltDependencies`。`src/agent/checkpoint.ts` 注释有说明。
4. **流式路径的 AI 消息 content 是 content-blocks 数组**：`typeof content === 'string'` 的过滤会把整个助手回复丢掉（真实故障：web 刷新后历史只剩提问）。一律用 `message.text` 取文本 —— `routes/agent.ts` 的 `toHistory` 与 `graph.ts` 的 `lastAiReply` 都踩过这个坑。
5. **打断/连发时旧流回调会「踩」新消息**：流回调必须**按消息 id** 更新（不能「更新最后一条」），且 `finally` 里仅当 `abortRef.current === controller` 才复位 busy —— 否则旧请求的收尾会污染新请求的状态（`chat.tsx` 注释里有完整推理）。
6. **type-only import 的类不能用于运行时 `instanceof`**：`import type { AIMessage }` 后写 `x instanceof AIMessage`，tsx 下侥幸能跑、vitest 下直接 `ReferenceError`。做运行时分型判断的类必须值导入（`routes/agent.ts` 有注释提醒）。

## 7. 动手练习（从易到难）

1. **接入一个现成 skill**：`skills/dms-websql` 已有脚本与 SKILL.md —— 仿照 `byteplus.ts` 写一个只读工具（spawn + 凭证注入 + 截断），补测试。
2. **给任意轮加操作**：目前撤回/重新生成只支持最后一轮；研究 `RemoveMessage` 能否撤回中间任意一轮（注意其后的消息也要一并处理）。
3. **换模型**：`.env` 改成 DeepSeek（`OPENAI_BASE_URL=https://api.deepseek.com/v1`、`OPENAI_MODEL=deepseek-chat`）验证问答与流式。
4. **读图**：把 `graph.ts` 的 `toolsCondition` 换成自定义路由函数，加入「连续 3 次工具调用后强制收束」规则。
5. **观察存储**：启动后 `sqlite3 apps/server/data/agent.sqlite '.tables'`，找出 checkpoint 表，理解快照怎么存；再用 `threads.ts` 的 SQL 对照侧栏数据。
6. **上下文裁剪实验**：把 `AGENT_MAX_INPUT_TOKENS` 调到很小（如 200），多聊几轮，观察 `FakeChatModel` 测试里模型实际收到的消息列表变短。
7. **进阶**：给写操作（如 BytePlus 建分群）加 LangGraph `interrupt` 人工确认流 —— 对比 `sp_send_signal` 的「工具层双步确认」实现，理解两种人工闸门的取舍。
